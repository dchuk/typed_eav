`QueryBuilder.filter` passes raw query values straight to Arel/ActiveRecord for `:eq`, `:not_eq`, `:gt`, `:gteq`, `:lt`, `:lteq`, and `:between` - `field.cast` is never called. A value the write path rejects (`"7.5"` for an Integer field) is silently accepted and coerced by the column's AR type; a value the write path normalizes (`" 7 "`) may not be normalized on query.

Add a single casting gate in `QueryBuilder` (this file is the sole SQL chokepoint for scalar filters) that, for the comparison operators listed above, routes the incoming value through `field.cast` and:
  - raises `ArgumentError` with a clear message naming the operator, the field name, and the rejected value when the cast reports invalid - mirroring the existing `ArgumentError` raised by the operator-validation gate at the top of `filter`;
  - uses the CASTED value for the SQL when the cast succeeds, so write-side normalization (whitespace stripping, type coercion) applies identically on the query side.

Preserve exactly, do not route through the new gate:
  - `:is_null` / `:is_not_null` (no value), `:contains` / `:not_contains` / `:starts_with` / `:ends_with` (substring patterns, not domain values), `:any_eq` / `:all_eq` (jsonb containment), and `:references` (already casts explicitly with its own `base.none` semantics);
  - NULL semantics: a `nil` query value on `:eq` / `:not_eq` must keep emitting today's `IS NULL` / tri-valued-logic-safe SQL - `cast(nil)` returns `[nil, false]`, so make sure the gate does not turn a legitimate nil into a raise or change the emitted SQL;
  - the operator-validation gate and `field.class.operator_column(operator)` column resolution.

Risk control: this gate applies to every field type, so run the FULL suite before committing. If an existing, documented behavior for a non-Integer type (e.g. a Boolean or Date query value that today reaches the column type raw) regresses, narrow the gate rather than changing the existing spec - the public query contract is preserved, and the agreement being repaired is the write/query mismatch, not a broader coercion redesign. Record any narrowing and its reason in the plan summary.

Then remove the `pending(...)` line from the "IMPROVEMENT PROGRAM 5" reproduction only. Same commit.

Tighten the guard to accept exactly two shapes: a `Range`, or an `Array` of exactly two elements. Anything else - including Arrays of size 0, 1, or 3+ - raises `ArgumentError` at the validation gate with a message that names `:between` and states the accepted shapes. Do not change the emitted SQL for well-formed input: a `Range` and a two-element `Array` must still produce `arel_col.between(first..last)` exactly as today.
