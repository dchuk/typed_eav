### D. Major query SQL shapes

Two-altitude split (ADR-0002), confirmed by direct read of both files:

- **`TypedEAV::QueryBuilder.filter(field, operator, value)`** (`lib/typed_eav/query_builder.rb:32`) — the ONLY place that emits SQL for a scalar filter. Validates `operator` against `field.class.supported_operators` first (raises `ArgumentError` with the allowed list), resolves the physical column via `field.class.operator_column(operator)`, scopes to `TypedEAV::Value.where(field: field)`, then a big `case operator` dispatches to Arel: `:eq`/`:currency_eq` → `where(col => value)` (NULL-safe via AR's own `IS NULL`/`IS TRUE` emission); `:not_eq` → `where.not` OR `IS NULL` (tri-valued-logic-safe); `:gt`/`:gteq`/`:lt`/`:lteq` → `arel_col.gt/gteq/lt/lteq(value)` (raw Arel comparison, relies on the underlying AR column type to cast `value`); `:between` → `arel_col.between(value.first..value.last)` guarded only by `value.respond_to?(:first) && value.respond_to?(:last)`; `:contains`/`:not_contains`/`:starts_with`/`:ends_with` → `ILIKE`/`NOT ILIKE`-style `arel_col.matches`/`.does_not_match` with hand-rolled `%`/`_`/`\` escaping (`sanitize_like`); `:is_null`/`:is_not_null` → plain `where(col => nil)` / `where.not`; `:any_eq`/`:all_eq` → raw SQL string `"#{col} @> ?"` against jsonb (array containment for MultiSelect/array types); `:references` → `field.cast(value)` first (accepts AR record or id), `base.none` on invalid/nil FK else `arel_col.eq(fk)`.
- **`TypedEAV::FilterQuery`** (`lib/typed_eav/filter_query.rb`) — orchestrates MULTIPLE filters + scope resolution. `to_relation` branches on whether the resolved scope is the `ALL_SCOPES` sentinel (multimap: OR-across every field def sharing a name, via `union_entity_ids` `.reduce(:or)`) or a concrete `[scope, parent_scope]` tuple (single-scope: `Partition.definitions_by_name` picks ONE winning field per name via collision precedence, then `query.where(id: QueryBuilder.entity_ids(field, op, value))` per filter, ANDed via `.inject`). `include_missing: true` + `:is_null` composes a **set complement**: `query.where.not(id: <ids with a non-NULL value>)` rather than touching `QueryBuilder` — this is how "no row at all" is captured without a LEFT JOIN (ADR-0006).
- **`TypedEAV::EntityQuery#resolve_scope`** (`lib/typed_eav/entity_query.rb:225`) is the scope-resolution chokepoint feeding `FilterQuery`: `unscoped? → ALL_SCOPES`; explicit `scope:`/`parent_scope:` kwargs → `ScopeTuple.normalize_permissive` per axis, then the orphan-invariant narrows a dead-letter `parent_scope` to `nil`; otherwise ambient (`with_scope` stack → `Config.scope_resolver` → `[nil,nil]` or raise `ScopeRequired` if `require_scope`).

**1. Pending false assignment order**

- **Location:** `app/models/typed_eav/value.rb:354-369` (`apply_pending_value`, private) and `value.rb:118-123` (`value=`, `else` branch: `@pending_value = val`).
- **Mechanism:** `apply_pending_value` guards with `return unless @pending_value && field`. When a `Value` is constructed with `field:` unresolved at the moment `value=` runs (e.g. hash key ordering puts `value:` before `field:`, or `Value.new(entity: e)` then `v.field = f` later without re-triggering resolution), the value is stashed in `@pending_value`. If the caller's intended value is the **boolean `false`**, `@pending_value` literally holds `false`. Ruby's `false && field` short-circuits to `false` regardless of whether `field` is now present — so the guard treats "pending value is `false`" identically to "no pending value at all" (the ivar's default nil state) and **silently drops the assignment**: the typed column is never written, and `@pending_value` stays `false` forever (never cleared), meaning even a LATER explicit `field=` assignment plus a manual `send(:apply_pending_value)` call cannot recover it either (same falsy short-circuit each time).
- **Existing coverage:** `spec/models/typed_eav/value_spec.rb:765-785` ("late-field-assignment caveat") tests ONLY the `UNSET_VALUE` sentinel path (`@pending_value` holding the frozen sentinel object, which IS truthy) — it never exercises a literal `false` pending value. No existing spec touches this.
- **Repro shape:** Build a `boolean_field` factory instance; construct `TypedEAV::Value.new(entity: contact, value: false)` (field omitted from the constructor hash so `value=` hits the `else` stash branch), then assign `field=` and call the same public flow the class documents (or directly assert on `@pending_value`/`.value` after invoking the resolution path) — expect `value.value` to equal `false`; currently it is `nil`. Alternately/better: reuse the SAME shape as the existing "late-field-assignment" spec (`described_class.new(entity: contact)` then `v.field = field; v.send(:apply_pending_value)`) but with a boolean field and `v.instance_variable_set(:@pending_value, false)` — assert `v.send(:apply_pending_value)` followed by `v.value == false`. Uses only `:boolean_field` / `:contact` factories, no changes needed.
- **Already-correct?** No — confirmed defect.

**2. Invalid-cast persistence**

- **Location:** `app/models/typed_eav/value.rb:388-412` (`validate_value`, private).
- **Mechanism:** `validate_value` checks `if @cast_was_invalid` FIRST, adds `errors.add(:value, :invalid)`, then **as a side effect resets `@cast_was_invalid = false`** before `return`ing. This flag is a genuinely one-shot "self-consuming" gate: the first time `valid?`/`invalid?` is evaluated after an invalid `value=` assignment, the error fires correctly — but the ivar is now permanently `false`. Any SUBSEQUENT validation run on the same in-memory object (e.g. a caller pattern like `if value.invalid? then render_form else value.save end`, or simply calling `.valid?` twice, which is common in Rails form-preflight code, or ANY validation callback ordering that runs `validate_value` more than once) will NOT re-detect the cast failure. Since `write_value` already wrote the (typically `nil`) casted value to the column on the ORIGINAL invalid assignment, and the field's `required?`/`validate_typed_value` checks pass cleanly on `nil` for non-required fields, the record **validates as fully valid on the second check and persists a nil/partial row** — even though the original input was cast-invalid and should have been permanently rejected.
- **Existing coverage:** No test in `spec/models/typed_eav/value_spec.rb` calls `.valid?`/`.invalid?` more than once on the same invalid-cast object, or exercises `@cast_was_invalid` directly — confirmed via grep (`cast_was_invalid` and `\.valid?` patterns return zero hits in `value_spec.rb`).
- **Repro shape:** `value = TypedEAV::Value.new(entity: contact, field: integer_field); value.value = "abc"; value.valid?` (or `.invalid?`) once to trigger-and-consume the flag, THEN call `value.save` (or `value.valid?` again) and assert it now returns `true`/persists — this is the CURRENT (buggy) behavior; the desired/pending assertion is that the SECOND check should ALSO fail (`value.save` should return `false`, `value.errors[:value]` should still include `:invalid`, and no row should be persisted with `integer_value: nil`). Uses `:integer_field` / `:contact` factories only.
- **Already-correct?** No — confirmed defect; subtle (order-of-validation-call-dependent).

**3. Exact-partition Field and Section ordering**

- **Location:** `app/models/typed_eav/field/base.rb:528-544` (`reorder_within_partition`, private) and the byte-for-byte-duplicated `app/models/typed_eav/section.rb:111-124`. Both call `for_entity(entity_type, scope: scope, parent_scope: parent_scope)` (`field/base.rb:123-129` / `section.rb:25-31`).
- **Mechanism:** `for_entity` is deliberately WIDENED for lookup/visibility purposes — `where(entity_type: et, scope: [scope, nil].uniq, parent_scope: [parent_scope, nil].uniq)` — so that global (scope=NULL) field definitions are visible alongside a tenant's scoped ones (the three-way collision-precedence contract, ADR-0002/`Partition`). `reorder_within_partition` REUSES this same widened scope as the "siblings" set for `move_higher`/`move_lower`/`move_to_top`/`move_to_bottom`/`insert_at` and their shared `normalize_partition_sort_order`. This means moving a field within an EXACT partition (e.g. `scope: "t1", parent_scope: nil`) also locks (`FOR UPDATE`), re-sorts, and **renumbers `sort_order` on GLOBAL fields (scope: nil) that happen to share the same `entity_type`** — the widened set is correct for read-time collision resolution but wrong for reorder-time sibling identity, which should be the EXACT `(entity_type, scope, parent_scope)` tuple only.
- **Existing coverage:** `spec/models/typed_eav/field_spec.rb:1111-1143` ("partition isolation") tests two DISJOINT non-null scope values (`"t1"` vs `"t2"`, and `parent_scope: "w1"` vs `"w2"` both under `scope: "t1"`) — neither scenario exercises the widening bug, because `for_entity(et, scope: "t1")` does NOT match rows with `scope: "t2"` (both are non-null and different). The bug only manifests when one partition is GLOBAL (`scope: nil`) and the other is SCOPED but sharing the same `entity_type` — a combination the existing tests never construct. `spec/regressions/review_round_4_parent_scope_spec.rb` covers three-way COLLISION PRECEDENCE for `where_typed_eav`/definition resolution, not ordering.
- **Repro shape:** Under one `entity_type` (e.g. a fresh dedicated string like the existing tests' pattern of unique `entity_type` fixtures, e.g. `"OrdExactPartition"`), create a GLOBAL field (`scope: nil`) and a SEPARATE scoped field (`scope: "t1"`) with known `sort_order`s. Call `move_higher`/`move_to_bottom` on the scoped field and assert the GLOBAL field's `sort_order` is UNCHANGED — mirroring the existing "does not affect a different scope partition" test's structure exactly but substituting `scope: nil` for one side. Currently this assertion FAILS (the global field's `sort_order` gets renumbered as a side effect). Uses `:text_field` factory only (same pattern as `make_partition` helper already defined in `field_spec.rb`, though that helper is local to that spec file and can't be reused across files without a spec_helper change — the new spec should inline its own minimal 2-field setup rather than importing `make_partition`).
- **Already-correct?** No — confirmed defect; also present symmetrically in `Section`.

**4. One-shot version-group correlation under object reuse**

- **Location:** `app/models/typed_eav/value.rb:153` (`attr_accessor :pending_version_group_id`), `lib/typed_eav/bulk_write.rb:261-273` (`stamp_pending_version_group_ids`), `lib/typed_eav/versioning/subscriber.rb:145` (`version_group_id: value.pending_version_group_id || context[:version_group_id]`).
- **Mechanism:** `pending_version_group_id` is documented as a "TRANSIENT in-memory ivar" meant to correlate ONE save's version row to its bulk-write's UUID. `stamp_pending_version_group_ids` sets it (`value.pending_version_group_id = uuid if uuid`) immediately before `record.save` inside a bulk call. Confirmed via grep across `lib/` and `app/`: the ivar is **written in exactly one place and never reset to `nil` anywhere** — not after `write_version_row` reads it, not after the bulk transaction commits. Because `Subscriber#write_version_row` reads it with `value.pending_version_group_id || context[:version_group_id]` (the ivar wins via `||` whenever it is truthy), any Value object instance that was PREVIOUSLY involved in a bulk write (so its `pending_version_group_id` was stamped to UUID-A) and is then REUSED for a completely separate, later, standalone save (e.g. `value.value = new_val; value.save!`, with no bulk context and possibly no `with_context` at all, or a DIFFERENT `with_context(version_group_id: uuid_b)`) will still have its version row stamped with the STALE `uuid_a` — the `||` never lets the fresh `context[:version_group_id]` (or the correct "no correlation" NULL) win, because the stale ivar is still truthy. The correlation is meant to be one-shot per save but leaks indefinitely across the object's lifetime.
- **Existing coverage:** `spec/lib/typed_eav/bulk_write_per_record_spec.rb` and `spec/lib/typed_eav/bulk_operations_spec.rb` exercise bulk calls in isolation; none reuse a Value object for a SECOND, non-bulk save afterward and assert its `version_group_id` on the second write. `CONCERNS.md`'s documented "sharp edge" is a DIFFERENT (already-acknowledged, Hash-collision) issue on `execute_per_record`'s outer Hash-keyed API — not this ivar-staleness issue, which affects `execute` (pair-shaped) too since it's at the `Value` object level, one layer beneath the record-pairing distinction.
- **Repro shape:** Use `:contact` + `:integer_field`. Perform a bulk write via `Contact.bulk_set_typed_eav_values([contact], { "age" => 1 }, version_grouping: :per_record)` with `TypedEAV::Config.versioning = true` and the contact's class registered `:versioned` (mirror the setup in `spec/lib/typed_eav/bulk_write_per_record_spec.rb` / `spec/models/typed_eav/value_versioning_integration_spec.rb`, needs `:real_commits` + `:event_callbacks` metadata per existing convention). Capture the Value object and its FIRST version's `version_group_id` (UUID-A). Then, OUTSIDE any bulk call and OUTSIDE any `with_context`, do `value.value = 2; value.save!` directly on the SAME in-memory `value` object. Assert the SECOND `ValueVersion` row's `version_group_id` is `nil` (no bulk context this time) — currently it is UUID-A (stale leak).
- **Already-correct?** No — confirmed defect. Note: the PAIR-SHAPED design of `execute`/`execute_pairs` (handling `[record, record]` duplicate instances within ONE bulk call) is a DIFFERENT, deliberately-solved problem — that part is already correct and should NOT be force-pended; only the cross-call ivar staleness described above is the defect.

**5. Field/query Integer casting agreement**

- **Location:** write-side: `app/models/typed_eav/field/integer.rb:17-28` (`cast`); query-side: `lib/typed_eav/query_builder.rb` — every comparison operator (`:eq`, `:gt`, `:gteq`, `:lt`, `:lteq`, `:between`) passes the RAW input value straight to Arel/ActiveRecord (`arel_col.gt(value)`, `base.where(col => value)`, `arel_col.between(value.first..value.last)`) with **no call to `field.cast`** anywhere in `QueryBuilder`.
- **Mechanism:** `Field::Integer#cast` is strict and explicit: `raw.to_s.strip` (trims whitespace), `BigDecimal(str, exception: false)` parse, rejects `nil` parse AND rejects any value where `bd.frac != 0` (fractional strings like `"3.7"` are marked INVALID, not truncated — locked behavior, confirmed by `spec/regressions/known_bugs_spec.rb` "ANALYSIS 3.1: Integer should reject decimal input"). The QUERY path has no equivalent gate — a filter like `Contact.where_typed_eav(name: "age", op: :eq, value: "3.7")` or `op: :gt, value: " 7 "` bypasses `Field::Integer#cast` entirely and relies on whatever `ActiveRecord::Type::Integer#cast` (the bigint column's own AR type) happens to do with that string — which may silently truncate, silently NULL, or otherwise diverge from the field's write-side contract. This is a genuine WRITE/QUERY casting-contract mismatch: the value you cannot WRITE (rejected as invalid) may be silently accepted (and coerced differently) when used to QUERY, and values that pass write-side normalization (whitespace-stripped) may not receive the same normalization on the query side.
- **Existing coverage:** `spec/lib/typed_eav/query_builder_spec.rb` has extensive operator-matrix coverage but no test asserting that a fractional-string or whitespace-padded query value is REJECTED or NORMALIZED consistently with `Field::Integer#cast`.
- **Repro shape:** Create an `:integer_field`, create a Contact with a legitimately-cast value (e.g. `value.value = 7`). Then query `Contact.where_typed_eav([{ name: field.name, op: :eq, value: "7.5" }])` (or `:gt`, `"3.7"`) and assert it raises/rejects (mirroring the write-side `field.cast("3.7") == [nil, true]` contract) OR returns a deterministically-defined empty/matching result — the pending spec should assert whatever the write-side contract implies (reject, don't silently truncate-and-match). This documents the desired AGREEMENT rather than presupposing the exact fix mechanism (which is Sol High's call at repair time — could route query values through `field.cast` first, could special-case `:eq`/`:between`, etc.).
- **Already-correct?** No — confirmed structural mismatch (write path validates via `field.cast`; query path never calls it).

**6. Strict `between` input shape**

- **Location:** `lib/typed_eav/query_builder.rb:96-102`.
- **Mechanism:** `unless value.respond_to?(:first) && value.respond_to?(:last); raise ArgumentError; end` — this only checks that the value RESPONDS to `#first`/`#last`, not that it represents exactly two bounds. `Range` and `Array` both pass. A **3+ element Array** (`[1, 2, 3]`) passes the guard and silently uses `1..3` (ignoring the middle element with no warning). A **1-element Array** (`[5]`) passes and silently produces the degenerate range `5..5`. A **0-element Array** (`[]`) passes the `respond_to?` guard (Array always responds to `first`/`last`) and produces `nil..nil`, which Arel/Postgres will likely error on downstream (an uncontrolled, unclear failure far from the actual input-validation site) rather than a clean `ArgumentError` at the API boundary.
- **Existing coverage:** `spec/lib/typed_eav/query_builder_spec.rb:419-433` ("`:between` input validation") tests exactly THREE cases: scalar `42` (correctly rejected), `Range` (correctly accepted), and a well-formed 2-element `Array` (correctly accepted). **No test exercises a malformed Array size** (0, 1, or 3+ elements) — confirmed by full read of that describe block.
- **Repro shape:** `expect { QueryBuilder.filter(field, :between, [1, 2, 3]) }.to raise_error(ArgumentError, /between/)` and the same for `[5]` and `[]` — currently none of these raise (or the 0-element case raises a DIFFERENT, unclear error deep in Arel rather than the intended `ArgumentError` at the validation gate). Uses `:integer_field` factory, matching the existing describe block's `let!(:field)` pattern.
- **Already-correct?** No — confirmed defect (loose shape validation).

**7. Full default-domain validation**

- **Location:** `app/models/typed_eav/field/base.rb:436-444` (`validate_default_value`, private).
- **Mechanism:** `validate_default_value` ONLY calls `_, invalid = cast(raw)` and checks the `invalid` flag from `cast` — it never calls `validate_typed_value(record, val)`, the SAME per-type domain validator that every live `Value#validate_value` runs (range bounds via `RangeBounded#validate_range`, option-list membership via `Optionable#validate_option_inclusion`/`validate_multi_option_inclusion`, string length/pattern via `ValidatedString#validate_length`/`validate_pattern`, array size via `validate_array_size`, etc.). Concretely: a `Field::Integer` with `options: { min: 0, max: 10 }` can be saved with `default_value_meta: { "v" => 999 }` and `field.valid?` returns `true` (999 casts cleanly as an Integer, so `cast(999).last == false`) — the out-of-range check (`validate_range`, only reachable via `validate_typed_value`) never runs against the default. Similarly a `Field::Select` (Optionable) can have a default value that is NOT one of its `allowed_option_values` and still pass Field validation. Downstream, `apply_default`/`backfill_default!` (`field/typed_storage.rb:154-156`, `field/base.rb:351-380`) write this UNVALIDATED default DIRECTLY to the typed column, bypassing `Value#value=`'s cast+`validate_typed_value` pipeline entirely (by design, to avoid re-casting an already-cast default) — so an out-of-domain default silently propagates to every entity's typed column with ZERO validation ever having run against it, at either Field-save time OR Value-apply time.
- **Existing coverage:** `spec/models/typed_eav/field_spec.rb:632-656` ("Field default values") tests ONLY cast-validity (`"not_a_number"` → invalid) and a valid text default — confirmed by full read: no test sets a default outside declared `min`/`max`, or a Select default not in `allowed_option_values`, or a string default violating `min_length`/`max_length`/`pattern`.
- **Repro shape:** `field = build(:integer_field, options: { "min" => 0, "max" => 10 }); field.default_value_meta = { "v" => 999 }; expect(field).not_to be_valid` — currently `field.valid?` is `true`. A second case: `field = build(:select_field); field.default_value_meta = { "v" => "not_a_real_option" }; expect(field).not_to be_valid` (note: `:select_field`'s options are created via `after(:create)`, so this needs `create(:select_field)` then reassigning `default_value_meta` and re-validating, since options must exist first for `allowed_option_values` to be non-empty). Uses `:integer_field` / `:select_field` factories only.
- **Already-correct?** No — confirmed defect (default validation is cast-only, not full-domain).

### F. Baseline helper design (`bench/database_baseline.rb`)

Design constraints from the ROADMAP/context-scout contract: read-only, dependency-free beyond current Rails/ActiveRecord/pg, no DDL/mutation/ANALYZE/VACUUM/stat reset, deterministic JSON output with sorted keys, empty-database caveats called out explicitly.

**Catalog/stat sources to read (all pure `SELECT`s against Postgres system catalogs/views):**
- `pg_indexes` (or `pg_index` joined to `pg_class`/`pg_am`) — exact index definitions (`indexdef`) for `typed_eav_fields`, `typed_eav_sections`, `typed_eav_options`, `typed_eav_values`, `typed_eav_value_versions`. `indexdef` gives the literal `CREATE INDEX ...` text including `WHERE`/`INCLUDE`/`opclass` clauses — cheap and precise, matches what the migrations declare.
- `information_schema.columns` (or `pg_attribute`/`pg_type`) — column definitions per table (name, type, nullable, default) — a portable read that doesn't require raw catalog OIDs.
- `pg_constraint` — the two new CHECK constraints from `20260712000000_enforce_parent_scope_invariant.rb` (`chk_te_fields_parent_scope_requires_scope`, `chk_te_sections_parent_scope_requires_scope`) plus FK definitions (e.g. `ON DELETE SET NULL` / `ON DELETE CASCADE` per the cascade-policy migration) — worth capturing since Phase 1's Gate cares about preserving these contracts.
- `pg_settings` — a curated subset of planner-relevant settings (`work_mem`, `shared_buffers`, `random_page_cost`, `effective_cache_size`, `default_statistics_target`, `max_connections`, `server_version`) — read-only `SELECT name, setting, unit FROM pg_settings WHERE name = ANY(...)`, never `ALTER SYSTEM`/`SET`.
- `pg_stat_user_tables` — `n_live_tup`, `n_dead_tup`, `seq_scan`, `idx_scan`, `last_vacuum`/`last_analyze` per typed_eav table — READ ONLY (do NOT call `ANALYZE`/`VACUUM` to freshen these, per the explicit no-mutation contract; the JSON output should note these stats reflect whatever the DB's autovacuum/last-analyze state happens to be, which may be stale/zero on a freshly-migrated empty test DB).
- `pg_total_relation_size(oid)` / `pg_relation_size` / `pg_indexes_size` — bytes-per-table and bytes-per-index, read-only functions (no mutation).
- Row counts: plain `SELECT COUNT(*) FROM <table>` per typed_eav table (cheap on a small/empty DB; the contract's "empty-database caveats" section should explicitly state these counts and the resulting bytes-per-logical-value figure are meaningless/undefined on a zero-row table and must not be treated as representative — Phase 2's ROADMAP goal explicitly requires "a larger isolated volume/host" for decisional evidence).

**Bytes-per-logical-value computation:** `pg_total_relation_size('typed_eav_values') / GREATEST(row_count, 1)` (guard divide-by-zero explicitly) plus a companion field documenting `row_count == 0` so downstream readers know the ratio is undefined/placeholder rather than silently trusting a `0/1` artifact.

**Determinism:** run against `spec/dummy`'s existing test-env DB config (`spec/dummy/config/database.yml`, `RAILS_ENV=test` matching `spec_helper.rb`'s pattern), require only `active_record`/`pg` (already gemspec dependencies — no new gem), sort all Hash keys before `JSON.generate`/`.to_json`, and SEPARATE deterministic content (schema/index/constraint definitions — stable across runs) from inherently-volatile content (row counts, `pg_stat_user_tables` snapshot, `pg_settings` values, wall-clock timestamp) into distinct top-level JSON keys (e.g. `"schema"` vs `"runtime_snapshot"`) so the committed `bench/results/phase-0-baseline.json` doesn't churn on every re-run for reasons unrelated to actual schema changes — OR explicitly document that the file WILL be regenerated (not diffed) each time it's committed, whichever the Gate 1 contract implies. Given the ROADMAP wording "emits deterministic ... JSON" (not "byte-identical JSON every run against a live DB"), the safer read is: deterministic KEY ORDERING and STRUCTURE (sorted keys, stable schema description), not necessarily byte-identical volatile numeric fields across DB states — the helper's own header comment should state this interpretation explicitly since Phase 0B's stop-condition list includes "missing exact definitions/settings/counts/caveats" (implying the numeric fields ARE expected, just not asserted byte-identical).

**Running it:** invoke via `bundle exec ruby -r./spec/dummy/config/environment bench/database_baseline.rb` (mirroring the CI "Create database and run migrations" step's `bundle exec ruby -e '...'` pattern of loading the dummy environment) OR have the script `require_relative` the dummy environment itself with a documented `RAILS_ENV=test` expectation — needs an explicit decision but the dummy app is the only Rails environment this gem ships, so it is the correct/only target.

## Relevant Patterns

- **The `for_entity` widen-vs-exact distinction (class 3) is a reusable pattern to watch for elsewhere.** Any future partition-aware helper that calls `for_entity(...)` for a LOOKUP purpose is correct-by-design; any helper that reuses it for an EXACT-PARTITION SIBLING SET (uniqueness checks, reordering, per-partition aggregate counts) needs its own exact-tuple query instead. Section mirrors Field byte-for-byte by DELIBERATE inline-duplication convention (documented in `section.rb`'s comments) — so the fix for class 3 must land symmetrically in both files in the same commit/PR to honor that convention, not just in `Field::Base`.
- **The transient-ivar pattern** (`@cast_was_invalid`, `pending_version_group_id`, `@pending_value`) is used three times in `Value` for different purposes, and TWO of the three (classes 1, 2, 4) have subtle lifecycle bugs (falsy-collision, self-consuming reset, never-cleared). Any repair should audit whether the THIRD instance (`@pending_value` itself, independent of the `false`-specific bug) has similar edge cases — e.g., is `@pending_value` ever left stale across multiple `initialize` calls on the same object (it shouldn't be, since `initialize` only runs once per object), but the repair for class 1 should double check it doesn't introduce a new staleness issue for class 4's ivar-reset pattern.
- **Existing regression-spec convention is strong and directly reusable**: `spec/regressions/*.rb` files consistently pair a `pending`-style block (or, per the CURRENT convention where all `known_bugs_spec.rb` bugs are now fixed and de-pended, a comment explaining "(FIXED)") with a `describe "ANALYSIS N.N: ..."` or `describe "REVIEW: ..."` string title referencing an analysis identifier — Phase 0A's new file should follow this exact naming/pending convention (`describe "IMPROVEMENT PROGRAM 1: pending false assignment order", :some_metadata do ... pending("...") { ... } end` or `xit`) so it reads as part of the same lineage.
- **`RSpec/DescribeClass` is pre-excluded for `spec/regressions/**/*`** — no RuboCop friction for the new file's string-based `describe` blocks.
