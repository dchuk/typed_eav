  <action>
Write a SHORT ADR (`docs/adr/0007-visibility-versus-mutation-relations.md`) following the format of the existing `docs/adr/0001`..`0006` files - read one first and match its headings, tone, and length. Content:
  - CONTEXT: `for_entity` is deliberately widened so global (scope NULL) definitions stay visible alongside a tenant's scoped ones, which is required for three-way collision precedence (ADR-0002 / ADR-0006). Reusing that same relation as the sibling set for a mutation silently expanded the blast radius of a reorder to rows in other partitions.
  - DECISION: this codebase distinguishes two relation kinds. A VISIBILITY relation answers "which definitions can this caller see?" and is deliberately widened. A MUTATION relation answers "which rows am I allowed to lock and rewrite?" and must be the exact `(entity_type, scope, parent_scope)` tuple. `for_entity` is the visibility relation; `for_exact_partition` is the mutation relation. A widened relation must never be the sibling set of a write.
  - CONSEQUENCES: any future partition-aware helper picks its relation by intent, not by convenience; uniqueness checks, per-partition aggregates, and reorder/renumber paths all use the mutation relation; the widened relation stays available and unchanged for reads. Name the regression test that catches a relapse.
  - SCOPE NOTE: this ADR is about relation choice only. It does not change tenancy semantics, collision precedence, or any public API.

Then add a row to the `docs/improvement-program.md` status tracker recording the ADR (phase, task, owner, status, dependencies, decision, evidence, commit, follow-up) and link it from the schema/ordering discussion.
